# Queensland Warning Mapping — reconstructed replacement

This is a new reconstruction dated **25 October 2026**, based on the requirements and implementation details retained in the project conversation. It is **not an exact recovery** of the lost `giswatidid/Mapping` repository. The last recorded original commit was `3e1e35a132f7ebd0e14db338f56d0fa1900e8e3d`; its source was not available for comparison.

The complete app is static HTML, CSS and JavaScript. No build step, application server, npm dependencies or private credentials are included. Keep all files together.

The interface follows the shared situation-board styling in [qldpoweroutages](https://github.com/gowlettluke/qldpoweroutages) and [qld_only_isolation](https://github.com/gowlettluke/qld_only_isolation): neutral grey/white surfaces, red accents, compact square panels and controls, and a persistent light/dark theme. Theme colours are defined in `styles.css`; map-export symbology is defined separately in `js/renderer.js`.

## Try it locally

Extract the ZIP, open a terminal in this folder and run:

```sh
python3 -m http.server 8000
```

Open <http://localhost:8000/demo.html> to exercise the JPEG exports, report text and separate camera/gauge PDFs with clearly marked **synthetic** fixtures. This separate demonstration works without ArcGIS or live data. Open <http://localhost:8000/> for the actual app. Opening the HTML directly as a `file:` URL does not support its JavaScript modules.

For live operation, the entry page asks only for your ArcGIS organisation prefix. Continue to ArcGIS's own sign-in page; after authentication, the app opens and automatically checks its data connections. A unique registered warning/radar item is selected automatically. Only ambiguous or missing weather items expose a selection control; choose the correct owner and use **Recheck layers**. The app uses the recorded public OAuth client ID from `CONFIG.arcgis.clientId` in `config.js` automatically; users do not enter or edit it. Its availability and registered redirect URL still need checking by the app administrator. Do not enter tokens, passwords or private API keys in `config.js`.

The connection panel checks warning/radar rendering, LGA coverage, both outage providers, traffic events and major-road names, coast/border/locator sources, basemap metadata, camera lists and authenticated camera/district queries, plus flood reference layers. It does not fetch camera photographs. Warning, radar and LGAs must pass before map generation is enabled; optional failures are reported separately. Checks have deadlines and are cancelled on sign-out or a superseding check. No layer requests are made before sign-in, except in the separate synthetic demo which uses no live connections.

Private warning/radar definitions are read through authenticated ArcGIS PortalItems. Their registered `mapUrl`, existing query values, custom parameters, WMS version, item identity, native layer names and styles are retained for image requests. Direct images use IdentityManager-aware ArcGIS requests. If browser access fails, the renderer uses only the signed-in portal's configured `helperServices.printTask` Export Web Map task, with a transparent MAP_ONLY PNG overlay. It does not use a generic `/sharing/proxy` route or a hard-coded public printing service. Capabilities failure alone does not block this fallback. Both connection checks and map generation use this same renderer, and checks pass only after a correctly sized, canvas-readable image is returned. A successful fallback is identified in the connection panel.

Saved item and SDK sublayer lists can be display subsets. The app therefore verifies its configured native warning/watch IDs through real image requests even when those IDs are absent from the saved list. Loaded sublayer hints are retained alongside the saved definition. A newly requested flood layer uses its own/default style, rather than inheriting an unrelated saved storm style; a label-only sublayer cannot substitute for the warning area. Unknown unconfigured names and service-reported missing layers still fail.

A successful portal login alone does not prove the backing WMS can be reached. Private metadata and image failures are reported without request URLs or credentials. To investigate a remaining failure, provide the ArcGIS **item details page link** and the connection-panel message; never send tokens, private API keys or passwords. District discovery accepts Feature Service and Map Service items; cameras also support Web Map and Feature Collection items. Recorded camera names are tried in priority order, and aliases to the same service/layer are deduplicated. If distinct sources still match, choose the correct item in its connection card. A missing source can be supplied as an ArcGIS item-page link or ID; it is loaded through the signed-in portal. Runtime WMS definitions and camera/district choices are discarded on sign-out. A manually selected gauge item ID is remembered locally for its organisation; its data and credentials are not stored.

The two flood catchment-name checks use live BoM reference geometry where browser access is available, with verified bundled Queensland boundary data as a fallback. A fallback is explicitly labelled **Bundled BoM catchment reference boundaries**, with its retrieval date. These are static reference shapes for matching catchment names and product IDs; current notice membership comes from the Queensland-published BoM Land Warnings feed. The authenticated WMS supplies the map images. Refresh the bundled geometry with `python3 scripts/refresh-flood-references.py`, then commit both compressed datasets and their manifest together.

Camera discovery recognises the `QLD Flood Cameras` item title as well as its `Web Cameras - LIVE` service name. Separate image views at each location are retained. BCC photographs are resolved from the service's ArcGIS attachment metadata; connection checks fetch that metadata, not the photographs. Capture times are not inferred from feature edit times.

Selecting **Flooding** automatically loads current BoM warnings and watches once the core layers are ready. One option represents one warning product, containing all the catchments in its latest issue. A single notice is selected automatically. Compact names identify each group; **Read BoM warning** opens its full notice. Final warnings remain selectable until expiry. Expired, cancelled, superseded and test records are excluded. Fresh notice metadata and complete catchment matching are required: failed or cancelled loads cannot become a no-warning result. Generation rechecks notice membership and requires every selected catchment to appear in the WMS image. A verified absence of current notices permits a statewide map.

The user's 27 October screenshot confirms successful warning/radar image checks through the organisation print service, connected disaster districts and generated statewide maps. Current public camera metadata has also been checked against the revised adapters; signed-in camera-image retrieval and active-storm output still need a deployment check. [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md) records completed validation and the remaining live checks; the synthetic demo alone does not verify private services.

## Included behaviour

- Severe Thunderstorm, Severe Weather and Flooding tabs, with warning detection and regional context. Flood options follow current BoM warning products, grouping their catchments into one report selection.
- Warning + Radar and Warning + Infrastructure Impacts JPEGs composed from the same warning raster. Storm/weather products share an added warning outline; flood products retain the source's original colours, boundaries and patterns. Neighbouring warnings remain visible in the selected regional view; a white-backed navy dashed outline identifies the selected notice without changing its analysis footprint. Map layers are clipped to the map frame. The small Queensland locator uses the mainland coast/state shape, independently of LGAs.
- Flood area names draw above the map overlays, with white halos and space reserved around them for outage numbers. Native warning/watch label layers are requested separately from warning detection, with verified BoM catchment-name references as a fallback. The selected flood product's source legend is included when readable; unavailable legends are identified explicitly, without guessed severity colours or a generic yellow warning swatch.
- Native-resolution local warning detection, a scale bar, contextual framing, optional storm tracking on Warning + Radar, and source credits without filler such as “not supplied by source”. Radar retains its source resolution. Infrastructure outages use light-to-dark purple shading by reported customers. Number labels default to 100+ customers per outage; the Outage labels control offers all counts, 100+, 250+, 500+ or 1,000+. The exported legend records the colour bands and chosen label threshold. Smaller outages stay visible, unknown counts are grey, and report totals retain all eligible outages.
- Copyable report text grouped under Energex, Ergon and roads. Power figures use each provider's own current unplanned council counts, with one row per warning-intersected LGA and a total for those LGAs. Unmatched council rows retain the matched totals: their customer counts are flagged separately and excluded from warning-area totals, or included as separate rows in statewide reports. Map polygons do not assign report customers to councils. Verified empty sections state that no current outages or major road closures are reported in the selected LGAs. Failed, stale or incomplete data never becomes a zero-impact claim.
- Roads in the text are major-road full closures with short locations. Restrictions can remain on the infrastructure map. Friendly source names are clickable in the preview and rich clipboard; plain-text clipboard fallback retains URLs.
- Cameras inside the actual warning footprint on all three tabs, including the selected flood warning or watch area, loaded photos only on request, and a landscape PDF with overview, camera index, numbered photo links and back-links. Cameras in neighbouring flood areas or elsewhere in the warning LGAs are excluded. Flooding includes older photos by default; thunderstorm/severe-weather defaults exclude verified photos older than one hour. A Camera filter dropdown on every warning type offers all cameras, one-hour/twenty-four-hour age limits, unverified exclusions and verified-only age limits. The choice is remembered per warning type and updates the list and Camera PDF without regenerating maps. Original capture times remain labelled separately from retrieval times. Upstream unavailable-camera images are not rejected just because of their appearance.
- The Flooding tab loads **BOM Flood Gauges 15min QFD DataShare** through the signed-in ArcGIS portal using its confirmed item ID. Startup retries one failed gauge lookup automatically, and a manual gauge choice is remembered for that organisation. A third JPEG shows gauges inside the selected warning/watch footprint with `G1`, `G2` markers coloured by their reported classification. The gauge list keeps height, source classification/trend, observation time and feed-update time separate. Its optional connection card accepts an alternative item-page link if the configured item is unavailable.
- Gauges are grouped by river/tributary and ordered upstream to downstream using a bundled public BoM/Geofabric reference. Map numbers, the on-screen list, PDF table and graph pages share that order. Separate branches keep separate reaches; unmatched, moved or ambiguous gauges remain visible as **Order unconfirmed**. Network-reference failure affects ordering only. Refresh this static reference with `python3 scripts/refresh-gauge-flow.py`; it contains public station/network metadata, not live heights or private ArcGIS data.
- The reference also uses [BoM's published station directory](https://www.bom.gov.au/qld/flood/networks/section3.shtml) to fill missing AWRC aliases and river names, requiring the same station ID and a location within 250 metres. Its January 2022 publication date is recorded; current AWRC aliases are retained. Exact site-name matches require a nearby, unflagged network gauge on one unambiguous channel, preserving headwater/tailwater distinctions. Where several named channels lie within the existing 120-metre tolerance, a downstream relationship is published only if every plausible placement agrees. A connected branch is confirmed without implying an order between separate branches; disconnected ambiguous sites remain unconfirmed.
- Flood warnings group current catchment AACs using BoM’s published product IDs; flood watches group catchments by office and issue time. Only the newest issue of each warning supplies its scope. All its catchments contribute to the maps, affected LGAs, disaster districts, cameras and gauges. In Flooding, choose the BoM warning/watch above Generate maps before generating its products. Neighbouring warnings and inactive parent/reference catchments are excluded from report, camera and gauge selection. Other warnings from the displayed flood layer remain visible on the maps, while the extent stays fitted to the selected notice. River diagram layout stays grouped by connected river system. Native source colours and hatching identify warning severity; surrounding warnings use reduced opacity for context. A single navy outline follows the outside of the combined selected warning. The source legend is preferred; if unavailable, flood-warning maps use a labelled standard BoM category key. Flood-watch maps keep an explicit source-key notice if their own legend is unavailable.
- Compact river diagrams keep connected systems together and separate unrelated basins. Stations show a shared G number, short location name, source level and trend; river names identify the branches. Larger networks use balanced river/reach panels ending at their verified receiving gauge, with a link to that gauge's home diagram. Unconnected gauges remain in the map/index without additional diagram pages. PDF diagrams use vector text and lines for readable zooming; JPEG downloads remain available. Observation times, full classifications and source station IDs stay in the index. Reported “Below Flood Level” is recognised as below minor; classification is never inferred from a numeric height.
- Camera and Gauge PDFs have separate buttons and filenames. The gauge document contains a gauge map, river flow diagram sheets, a linked table of up to 20 gauges per page, and four graph images per page in a two-by-two grid. The camera document contains its own overview, linked index and photographs. Each button depends only on its own source and retrieves only its own images; both have their own progress and cancellation controls. The table shows station, level, source classification, trend and observation time; major rows are red, moderate yellow and minor green, with blue text for below-minor readings and grey for unknown readings. Gauges-only output works without cameras or available graph images; missing graphs keep their readings and a clear unavailable notice. Graph images come from layer fields or image/HTML popup templates and load only on request. If browser cross-origin access fails for a public BoM PNG, export can use the signed-in organisation's print service. Classification is never inferred from height, and graph paths are never invented from station IDs.
- Cancellable generation, independent report preparation, theme control and responsive layout. No camera/PDF diagnostic section in the main app.

Node.js 20 or newer is needed for development checks. The static reference builder and its tests use Python 3's standard library:

```sh
npm run check
npm test
python3 -m unittest discover -s tests -p '*_test.py'
```

The GitHub Actions workflow runs those checks on pushes and pull requests. The bundled jsPDF distribution is MIT licensed; see `vendor/jspdf.LICENSE`. This reconstruction does not assert a licence for the unavailable original source or for third-party map and camera data. Retain provider credits and comply with each provider's terms.

### Flood map presentation

Flood maps lead with the selected area name and the map purpose, with a clearly labelled map-generation time. Individual gauge observation times remain in the gauge list and PDF index. Warning-area colours have their own legend, separate from reported station classifications. Gauge references use white boxes with coloured status dots; stations at minor, moderate or major levels receive short names where space permits. The G numbers and PDF graph links are unchanged.

The topographic background and LGA lines are subdued. LGA strokes are clipped to Queensland mainland/island geometry for display, removing offshore administrative tails without changing the LGA analysis. Current populated places and named major channels for the selected warning are optional Queensland Government context sources; their failure does not block map generation. Closed roads use dark red lines with white casing, while restrictions use thinner neutral dashes. Surrounding infrastructure is less prominent and outage count labels focus on the selected warning.

The standard flood-warning key is verified against BoM’s [published “Flood Warning Extent and Severity” legend](https://www.bom.gov.au/sites/default/files/2025-10/foi30-167-released-documents-set-3.pdf), PDF page 169: major, moderate, minor, generalised, below minor and final warning. It explains warning areas; it never supplies gauge classifications or implies that the entire shaded area is inundated. Native warning imagery and analytical selection masks are retained unchanged.

Gauge status colours use one shared palette across maps, cards, river diagrams, PDF tables and synthetic chart thresholds: blue below minor, green minor, yellow moderate, red major and grey unknown. Darker text variants preserve readability on white, and numbers on yellow/blue station badges use dark text. Source classifications and original BoM graph images are unchanged.
